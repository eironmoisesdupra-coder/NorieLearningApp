# Public release packages

The [download page](../../branding/web/downloads.html) is published with the web
preview at <https://eironmoisesdupra-coder.github.io/NorieLearningApp/downloads.html>.
It reads the latest complete public release through the unauthenticated GitHub API.
If no release exists or the API is unavailable/rate limited, it explains the state
and links to GitHub Releases. It never substitutes expiring Actions artifacts.

## Build and publish

1. Update the version in [pubspec.yaml](../../pubspec.yaml), including its build
   number, and match the semantic version in
   [desktop/package.json](../../desktop/package.json). Merge the reviewed PR into
   `develop` through the established CI workflow.
2. Wait for **Flutter CI** and **Windows Desktop** to succeed for the exact merged
   commit. A successful PR build does not substitute for a `push` build on
   `develop`. The latest run of each workflow at that SHA must succeed.
3. Inspect the APK and Windows ZIP on supported devices, including offline use.
   The Windows CI already exercises the packaged app with networking blocked.
4. Create an annotated tag matching `vMAJOR.MINOR.PATCH` on that exact SHA and push
   that tag, for example `git tag -a v0.5.0 <full-sha> -m "NorieLearning 0.5.0"`
   followed by `git push origin v0.5.0`. This is an explicit publication action;
   preparing this workflow does not itself authorize publishing a release.
   Alternatively, push a `release/vMAJOR.MINOR.PATCH` branch at that tested SHA.
   This runs the same provenance checks and creates the version tag only after
   both platforms pass. Existing version tags must resolve to the exact revision.
   A single release concurrency group prevents branch and tag publication racing.
5. [Publish tested release](../../.github/workflows/release.yml) validates that the
   tagged commit belongs to `develop`, version numbers match, the repository is
   public, and both trusted same-repository CI runs passed at that commit. It
   downloads their existing packages without rebuilding them. No PR/fork artifact
   or unrelated successful revision qualifies.
6. The workflow uploads both packages, metadata, and SHA-256 checksums to a draft,
   then publishes the release. A previously published release cannot be replaced
   by this workflow. A failed draft can be retried with **Run workflow**, entering
   the existing tag, after correcting the cause. If source Actions artifacts have
   expired, rerun both exact-revision trusted CI runs first; do not relabel a
   package from another revision.
7. Verify the published download page on a phone-width viewport and open both
   links in a signed-out browser. Include both links, full revision, version,
   exact CI status, and any device-validation limitations in the handoff.

Version-specific durable links (replace `v0.5.0` with the actual published tag):

- Windows: `https://github.com/eironmoisesdupra-coder/NorieLearningApp/releases/download/v0.5.0/NorieLearning-Windows.zip`
- Android: `https://github.com/eironmoisesdupra-coder/NorieLearningApp/releases/download/v0.5.0/NorieLearning-Android.apk`

These links become available only after the release is published. Public GitHub
release downloads require no account. GitHub Releases retain these assets until a
maintainer removes them; Actions retention does not apply to release assets.

## Metadata and validation

[prepare_release.py](../../scripts/release/prepare_release.py) records the complete
pubspec version, tag, full source SHA, byte sizes, signing status, and SHA-256 of
both actual downloaded packages in `release-metadata.json` and the release notes.
The browser reads the notes via GitHub's API to avoid cross-origin restrictions
on fetching JSON release assets. It requires both exact version asset URLs and
matching byte sizes before enabling downloads. The displayed checksum lets users
independently verify their download; it is not a digital signature.

Run the focused checks with:

```text
python -m unittest discover -s test -p release_tools_test.py
node --test test/downloads_test.mjs
```

The package-collection job has read-only repository permissions. The publishing
job receives only validated workflow artifacts and never executes downloaded
application packages or scripts. Its `contents: write` scope is limited to that
job. Protect release tags and `develop` using repository rules appropriate to the
maintainers; this workflow does not change repository security settings.

## Current signing and installation limits

The Windows package is a portable Electron x64 build. The existing packager has
no Authenticode signing configuration. It is **unsigned**, and Windows may show
an unknown-publisher warning. Extract the entire ZIP and run `NorieLearning.exe`
without moving it away from its resources.

Android scaffolding is generated by `flutter create` in CI; the workflow does not
configure a production keystore. Flutter's generated release configuration uses
the debug signing key. The APK is therefore a **preview**, not a store-ready
production-signed release. Ephemeral CI machines can generate different debug
keys between runs, so an update may not install over an earlier APK. Uninstalling
can erase local learning data. A stable, securely provisioned production key and
an explicit data-preserving upgrade validation are still needed before reliable
public update distribution. Do not commit signing keys into the repository.

The Android minimum is API 24 (Android 7.0), set by the existing CI configuration.
Windows targets 64-bit Windows 10 or later. Core installed lessons are local;
downloading packages and optional online services need connectivity. This release
pipeline does not implement automatic updates, account provisioning, or store
submission, and it does not claim those services are production-ready.
